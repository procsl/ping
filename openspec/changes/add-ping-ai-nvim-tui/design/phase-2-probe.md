# 阶段 2 设计：管线探针

对应 `tasks.md` 阶段 2（任务 2.1–2.4）。架构决策见 `../design.md` D14。

> 本阶段是**变更的闸门**：通过则继续，失败则终止并回写结论。

## 为什么先做探针

完整方案要在阶段 3、4 之后才能验证「这条管线是否成立」：

```
模型 SSE → Flux → EventStream → NvimAdapter → msgpack-rpc → lua → buffer → 终端
```

其中有三处无法靠推理排除的不确定性：

1. `nvim --clean --listen` 与「继承 Java 的 stdin/stdout/stderr」能否同时成立；
2. `exec_lua` 往返延迟是否足以支撑逐批写入；
3. 流式 append 在真实终端（而非 headless）下是否触发性能问题。

探针只验证这三点，不实现组件、不实现布局、不实现工具确认。

## 探针内容

```
2.1  启动 nvim --clean --listen <addr>，Java 连接成功
       记录：启动耗时、连接结果、socket 路径

2.2  一次 exec_lua 往返
       lua: return 42
       Java: 收到 42
       记录：单次延迟、连续 100 次的中位数

2.3  一次流式 append
       向同一 buffer 灌入 1000 个片段（模拟 token）
       记录：总耗时、最大行长、进程 CPU、界面是否卡住

2.4  汇总结论
       通过：三项指标均在接受范围内 → 继续阶段 3
       失败：记录哪一项不成立、是否有替代方案 → 终止变更
```

## 通过标准（初值，需一次真实采样后回写）

| 指标 | 初值 | 说明 |
|---|---|---|
| 启动到可连接 | < 2s | 冷启动，不含下载 |
| `exec_lua` 往返中位数 | < 5ms | 本地 unix socket |
| 1000 片段总耗时 | < 1s | 不含模型产出时间 |
| 最大行长 | 受控（无 80 万字符级） | 对应 `neovim#34019` |

## 失败时的处置

- 不删除已完成的阶段 1（分发本身可用）。
- 在 `proposal.md` 记录探针结论与失败原因。
- 核心变更 `add-ping-ai-agent-core` 不受影响，仍可独立归档与使用。
